#### Design Specificity Verdict

**LLM assessment:** 绿色农业语义、田间拍照、黄绿检测框、证据绑定、知识库和拒答边界让界面具备真实产品特征；它不是纯模板。但结构仍大量依赖“暖白背景 + 大圆角白卡 + 绿色主按钮”的通用 SaaS 工作台语法，尚未把田间采样、证据强弱和双服务器病例归属转化为更独特、可一眼理解的视觉语言。

**Deterministic scan:** `detect.mjs` 扫描 `web/app` 得到 1 条 warning：`web/app/globals.css:280` 的训练监控进度条使用 `transition: width`。这是有效的布局动画问题，但只影响训练监控，属于 P3；检测器没有发现其他机械反模式。关键配色对比度为 4.84:1–7.20:1，均通过普通文本 WCAG AA。

**Visual overlays:** 浏览器能导航到实验室首页并确认正确 URL/标题，但响应式截图与样式采样两次超时；当前 Browser 只提供只读 evaluate，没有可用的脚本注入能力。因此没有可靠的用户可见 overlay，视觉回退信号为现有源码、响应式 CSS、成功页面导航和 CLI 检测结果。

#### Overall Impression

系统已经具备稳重、可信、证据优先的视觉基础，尤其适合农业辅助诊断这种高不确定任务。最大机会不是“换一套皮肤”，而是把双服务器归属、必填完成度和约 96 秒 CPU 分析等待这三件真实系统事实直接设计进主流程；它们目前比配色或圆角更影响用户信任。

#### Cognitive Load

8 项检查中有 2 项失败，属于中等认知负荷：植物病例会同时出现图片上传和 6 个字段决策，超过单个决策点建议的 4 项；上传、填写、等待和阅读结果虽然在视觉上分成两步，但第一步仍要求用户一次处理过多信息。分组、视觉层级和移动端单列处理通过，技术证据也已折叠，说明基础方向正确。

#### What's Working

- **状态语义克制而清楚：** 深绿负责可信和操作，琥珀负责补拍/不可用，红色负责错误；且状态均有文字，不只依靠颜色。
- **证据结构与产品责任一致：** YOLO 结果、综合分析、知识内容和拒答逻辑被分成独立层级，避免把百科内容伪装成本次图像证据。
- **可访问性基础扎实：** 用户文本已统一提升到约 14px，交互目标至少 44px，全局 `:focus-visible` 可见，移动端有固定底部导航，主要对比度通过 AA。

#### Priority Issues

- **[P1] 双服务器数据归属在公共 UI 中不可见且措辞错误**
  - **Why it matters:** 历史、趋势和页脚写“当前电脑”，实际数据按当前活动服务器隔离；管理员切换实例后，普通用户可能把病例列表变化理解成数据丢失。
  - **Fix:** 在公共页头或病例页明确显示“当前识别实例：实验室 CPU / 原 GPU”，把“当前电脑”统一改为“当前识别服务器”；历史空状态说明切换实例会看到另一套独立记录。
  - **Suggested command:** `$impeccable clarify`

- **[P1] 禁用的主按钮没有告诉用户还缺什么**
  - **Why it matters:** 植物病例最多需要图片加 6 个田间字段；按钮在缺项时不可点击，用户不能触发表单错误，只能逐项猜测。
  - **Fix:** 在按钮上方显示动态缺项摘要，例如“还需：图片、植物部位、生长阶段”；已完成分组给出轻量完成标记，字段附近保留简短条件说明。
  - **Suggested command:** `$impeccable clarify`

- **[P1] CPU 长耗时分析缺少等待预期和中断恢复**
  - **Why it matters:** 实验室 CPU 多模态稳定耗时约 96 秒。仅显示“正在综合两阶段证据”会让用户怀疑页面卡死；刷新或离开后也没有明确恢复路径。
  - **Fix:** 分析开始时明确“通常约 1–2 分钟”，先显示已保存病例编号和“可稍后从病例历史查看”；若不能安全取消，要明确说明。重进页面时按病例状态恢复进度，而不是重新提交。
  - **Suggested command:** `$impeccable harden`

- **[P2] 面向普通用户的说明泄漏模型术语**
  - **Why it matters:** “YOLO”“第二阶段证据”“provenance”要求用户理解内部架构，削弱了田间场景中的可读性。
  - **Fix:** 主路径改为“目标定位模型”“图片与田间信息核对”；技术名称只放在管理员端或折叠详情，并给出一句通俗解释。
  - **Suggested command:** `$impeccable clarify`

- **[P2] 结果页纵向层级过长且行动优先级不清**
  - **Why it matters:** 空结果区桌面高 610px、手机高 420px；形成结果后连续出现摘要、综合分析、知识、两个同等醒目的 22px 链接和技术详情，用户很难判断下一步先看什么。
  - **Fix:** 缩短空状态；结果顶部只保留一项主要行动（建议“打开诊断报告”），病例详情作为次级文本链接；综合分析和知识使用清晰目录或折叠层级，技术区保持最低权重。
  - **Suggested command:** `$impeccable distill`

#### Persona Red Flags

**Jordan（首次使用者）:** 选择作物后字段会变化，但没有“为什么出现这些字段”的解释；主按钮禁用时不显示缺项；“YOLO 决定最终类别”要求理解模型术语。Jordan 很可能在提交前停住，而不是看到现有的错误恢复能力。

**Sam（依赖无障碍技术）:** 标签、原生控件、焦点环和 44px 目标表现良好；但页头链接没有 `aria-current`，服务状态和表单下的阶段进度没有独立 `role=status`/live region，屏幕阅读器不一定及时宣布当前位置和长任务变化。

**Casey（分心的移动用户）:** 底部导航和单列表单适合单手操作；但表单不保存草稿，切走或刷新会丢失选择。约 96 秒等待没有“可离开并稍后查看”的承诺，长空状态和结果内容也增加手机滚动成本。

#### Minor Observations

- 公共导航缺少视觉 active 状态和语义 `aria-current="page"`。
- 报告正文仍大量使用 11px；在高分辨率屏幕尚可，但打印/PDF 和低视力场景偏小。
- 两个结果入口统一为 22px 后，与 23px 区块标题几乎同级，造成行动区过度放大。
- 训练监控的 `transition: width .4s ease` 应改为 `transform: scaleX()`，并补充 `prefers-reduced-motion`。
- CSS 中存在旧界面规则、Phase 9 规则和后置“functional hardening”覆盖；当前视觉能工作，但后续维护容易产生字号和断点漂移。

#### Questions to Consider

- 如果用户在首页只能记住一件系统事实，应该是“当前使用哪台服务器”，还是“模型为什么可信”？
- 植物病例的 6 个田间字段是否都必须在上传前一次完成，还是可以先选图，再逐组补充？
- 结果形成后，最希望用户先做的是阅读综合分析、查看防治知识，还是保存/打印报告？
